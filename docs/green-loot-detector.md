结果有 `found`、`absent_visible`、`uncertain` 三种。`absent_visible` 只表示**当前画面可见的装备列表**里没有匹配目标；它不证明目标怪物已被击杀、掉落已加载完，或列表没有需要滚动的隐藏部分。因此不能单独触发送败。实机自动化需另行验证首波结束、列表稳定和完整，再连续检查；若画面或时机不确定，暂停供人工判断。超过三行或出现滚动列表时，要先补齐翻页／滚动检测。

离线核对：用户游戏中的单行及三行无目标战利品列表最高均为 0.474；同游戏绿衣模板放入同布局列表得分 1.000，缩放到 80% 后得分 0.993，放在第三行仍为 1.000；来自视频的绿衣图标得分 0.984。后两项分别是合成列表与不同来源图像，**尚非实机出货后的战利品列表**。需要一张真实出货列表验证目标匹配，或在第一次自然出货时保留现场验证。

完整刷取控制还需要确认：首波／宝箱怪击杀的可观察信号，何时打开及关闭战利品列表，送败后的返回与重进流程，出货后的 FC／结算流程。这些未通过实机画面验证前，不应让检测结果驱动点击。

## 用户确认的目标流程（2026-10-14）

1. 进入深度 10 战斗后先观察右上角**战利品宝箱数量**。只要首次掉落数变为正数，就直接进入检查，省去 FC。讨伐数增长但战利品数仍为 0，经过等待后才考虑补一次右下角**第二个蓝紫色水晶 FC**。
2. 补 FC 后继续等待战利品数更新；不能点完立即判定无掉落。确认数量为正数后点击右上角战利品按钮，打开获得报酬列表，扫描当前可见的三行装备。
3. 识别到绿衣则锁定本局为通关模式。关闭列表后，每次能量足够且 FC 可用时释放同一个水晶 FC，直至通关，随后确认结算。
4. 确认无绿衣则锁定本局为送败模式。关闭列表后不再主动释放 FC，等待战斗失败；完成失败后的返回、重进，再从第 1 步重复。
5. 列表未稳定、面板不全、似是而非或检查时机不明时进入人工确认，不能自动送败，也不能自动通关。每天最多三次通关，因此不能用“全部通关”兜底。

待录屏验证的必要转移：首波清理的画面信号；FC 可用与能量足够的图像信号；失败页点击再挑战后的重进页面；胜利结算及绿衣实得确认。中央的限时宝箱与右上角战利品按钮要分别识别。

## 2026-10-14 第二段本机录屏：按掉落决定是否补 FC

`屏幕录制 2026-10-14 112018.mp4`（76.9 秒，1920×1080，30 fps）包含两次尝试。第一次未补 FC 就已有战利品 16 件，约 13 秒打开列表；检测器返回 `absent_visible`，最高匹配 0.497。第二次约 40–43 秒讨伐数已到 1/70、战利品仍为 0；约 43 秒水晶 FC 可用并被点击；约 46 秒能量归零、FC 正在生效，战利品仍为 0；约 52 秒战利品增加到 11，约 54 秒打开列表，检测器返回 `absent_visible`，最高匹配 0.479。由此可见，FC 后仍须等待掉落计数更新，不能立即检查空列表。

实现分支：战利品数量 > 0 → 直接看列表；数量持续为 0 且超过首波等待时限 → 等 FC 亮起后释放**一次**；释放后仍为 0 → 等待或人工确认，不按“无绿衣”送败。目标出现与否只能根据稳定、完整的列表判断。首波等待时限尚需实机调参，不能仅凭一次视频硬编码。两次尝试都以失败结算结束，未覆盖有绿衣的通关动作。

纯决策模块 `green_farm_policy.py` 已按上述两种开局分支实现，并用两段离线轨迹检查：首波自动出 16 件直接打开列表；零掉落时补一次 FC，等待到 11 件再打开列表。模块尚未连接游戏截图和点击，`panel_complete` 必须由后续视觉层独立确认，不能仅凭模板返回 `absent_visible` 就送败。
